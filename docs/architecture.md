# Архитектура
## Проект: «Спортивные секции: запись и расписание»

## Тип архитектуры
Монолит + MVC + слоистая

## Обоснование
- **Масштаб:** ≤ 500 пользователей в день — микросервисы избыточны.
- **Команда:** 1 разработчик — проще поддерживать монолит.
- **Сроки:** 4 недели — нужна быстрая разработка.
- **Технологии:** Flask (Python), Jinja2, SQLAlchemy, PostgreSQL.

## Слои приложения
1. **Presentation** — Jinja2 (HTML-шаблоны).
2. **Controller / API** — Flask (обработка маршрутов).
3. **Business Logic** — сервисы (модули Requests, Masters, Sections).
4. **Data Access** — SQLAlchemy (ORM, работа с PostgreSQL).
5. **Database** — PostgreSQL.

## Схема слоёв

Presentation (Jinja2)
↓
Controller (Flask routes)
↓
Business Logic (Services)
↓
Data Access (SQLAlchemy)
↓
Database (PostgreSQL)

1. Краткая теория
Модуль — логически целостная часть с чёткой зоной ответственности.

Coupling и Cohesion:

Coupling (связность между модулями) — должен быть низким.

Cohesion (связность внутри модуля) — должен быть высоким.

❌ Плохо	✅ Хорошо
Высокое coupling, низкое cohesion	Низкое coupling, высокое cohesion
Много связей между модулями	Одна чёткая связь через интерфейс
Типы модулей:

Бизнес: Auth, Lessons, Sections, Bookings.

Инфраструктурные: DB, Config, Logger.

Интеграционные: SMSGateway, PaymentGateway.

Правила выделения:

Один модуль = одна функция.

Модуль не зависит от UI.

Бизнес-логика не знает о БД напрямую.

Ошибки: God Object, циклические зависимости, UI знает о БД.
